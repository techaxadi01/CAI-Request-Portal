1. EXECUTIVE OVERVIEW & PROBLEM STATEMENT
================================================================================
The Centre for Artificial Intelligence (CAI) Requests Office at Christ University 
coordinates procurement and grant applications from faculty, research scholars, 
and postgraduate students across campuses.

Prior to this application, the office operated on a disjointed combination of:
• Campus-wise Excel workbooks (prone to cross-campus entry errors and data collisions)
• Informal email chains (attachments buried or misplaced)
• Disorganized WhatsApp threads with external specialists (multiple request replies 
  mixed into single chat feeds)

Key Operational Deficits Solved by this Portal:
• Files Lost / Overwritten: Every request maintains an immutable documents array 
  with file types, timestamps, sizes, and version tracking (<10 MB readable files).
• Ambiguous Status: Requesters can inspect real-time visual progress across all 6 
  workflow states without needing to visit or call the office.
• Wrong Campus Filing: Requests are strictly tagged to one of the 6 official 
  Christ University campuses, and the Coordinator dashboard features instant campus-filter 
  tabs to prevent cross-campus confusion.
• Courier Burden on Coordinator: The coordinator no longer forwards messy emails; 
  deficiencies are requested through structured modal forms with direct notifications.
• Specialist Usability: The external specialist (accustomed to WhatsApp-clean simplicity) 
  accesses a distraction-free review feed with high-contrast cards, zero technical 
  jargon, and masked applicant identities.

6. MONGODB ATLAS DATABASE SCHEMAS & CONFIGURATION
================================================================================
Database Name: CAI_Request_Portal
Cloud Provider: MongoDB Atlas (Replica Set Cluster)

1. User Schema:
   • name: String (required)
   • email: String (required, unique, lowercase)
   • password: String (stored as 60-character bcrypt salt hash)
   • role: String (enum: ['requester', 'coordinator', 'specialist'])
   • campus: String (Christ University Campus)
   • department: String (Default: 'COMPUTER SCIENCE')
   • designation: String
   • timestamps: true

2. Request Schema:
   • trackingId: String (unique, e.g., 'CAI-2026-001')
   • requesterId: ObjectId (ref: User)
   • requesterName: String
   • requesterEmail: String (masked for Specialist)
   • campus: String (6 official campuses)
   • department: String
   • shortTitle: String
   • category: String (Hardware, Software, Travel, Event, Research, Other)
   • otherPeopleInvolved: String
   • amount: Number
   • shortDescription: String
   • documents: [{ fileName, fileType, fileSize, uploadedAt, version }]
   • status: enum ['Submitted', 'Changes Requested', 'Under Specialist Review',
                   'Specialist Feedback Received', 'Decision Made', 'Completed']
   • coordinatorRemarks: String
   • coordinatorReviewedAt: Date
   • specialistAssigned: ObjectId (ref: User)
   • specialistAssignedName: String
   • coordinatorNoteToSpecialist: String
   • specialistReview: { recommendation, feedback, reviewedAt, specialistName }
   • finalDecision: { outcome, decisionNotes, decidedAt, decidedByName }
   • requesterConfirmed: Boolean
   • requesterConfirmedAt: Date
   • requesterConfirmationNote: String
   • timeline: [{ action, byName, byRole, timestamp, notes, badgeColor }]
   • timestamps: true

7. PASSWORDS & SECURITY: BCRYPT HASHING ARCHITECTURE
================================================================================
• Industry-standard bcryptjs hashing with dynamic salting (10 rounds).
• Mongoose pre-save hook in User.js automatically hashes plain-text passwords 
  prior to database persistence.
• Idempotence guard: Prevents double-hashing if an encrypted hash is already present.
• Database Seeding: Demo passwords ('password123') are pre-computed using 
  bcrypt.hashSync('password123', 10) before insertion.
• Authentication: user.comparePassword(candidatePassword) verifies hashes using 
  bcrypt.compare, rejecting invalid passwords with 401 Unauthorized.
• API Sanitization: Password fields are completely excluded from public API queries.
